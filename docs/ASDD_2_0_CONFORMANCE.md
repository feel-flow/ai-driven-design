# AI仕様駆動開発2.0 適合条件と試用シナリオ

本書は [標準仕様](ASDD_2_0.md) に対する検証方法を定める。**文書に方針が書かれていることと、実装が動くことを分けて評価する。** このチェックリストの公開自体は、公式実装の試用・配布完了を意味しない。

## 評価の記録

評価には、対象のリポジトリ・コミットまたは配布版、AIホストと版、選択構成、確認日時、手順、観測結果、証拠へのリンクを記録する。個人情報や会話全文は証拠に含めない。

結果は「合格」「不合格」「未検証」「適用外」を使う。適用外は、例えばCI無効構成でCIの実行を検証しない場合など、理由を明記する。**無効な機能が動かないことの確認は適用外にしない。** 静的検査・テストで確認した範囲と、実ホスト・外部連携で確認した範囲を別々に記録する。

## 共通適合条件

| ID  | 条件                                     | 合格を判断する証拠                                                                    |
| --- | ---------------------------------------- | ------------------------------------------------------------------------------------- |
| D1  | 事実・合意・提案・未決を区別する         | 未回答の事業要件を含む初期化で、推測が採用済み仕様やHookへ入らない                    |
| D2  | 対話は目的から進め、回答・委任を引き継ぐ | 既存資料と前の回答を利用し、判断を変えない重複質問をしない                            |
| D3  | 7観点を必要な文書へ配置する              | 最小構成と7文書構成の両方で検証・文書検索が動き、任意文書を必須にしない               |
| D4  | 一律デフォルトを強制しない               | カバレッジ数値やResult型を選ばない構成で、生成文書・AI設定・検証に強制がない          |
| D5  | 技術選定の根拠を記録する                 | 公式URL・確認日・採用系列・互換性・見送り理由を確認でき、確認失敗時に最新と断定しない |
| C1  | 一つの設定から機能が整合する             | ACE・振り返り・レビューの独立切替が生成物と実行に反映される                           |
| C2  | 無効な機能を実行・督促しない             | 新規構成のACE・自動振り返り無効時に関連処理・Hookからの実行提案が発生しない           |
| C3  | 確認モードは読み取り専用である           | `asdd-init --check` 前後で追跡・未追跡ファイルと外部状態が変わらない                  |
| C4  | 再実行・移行で手編集を守る               | 管理対象の手編集と未管理ファイルが残り、衝突を示す。途中中断後に重複生成しない        |
| C5  | 対応不能を有効扱いしない                 | 不正・未知の設定、未対応ホスト機能を明示し、黙った既定値化や成功報告をしない          |
| W1  | 一つの目的・成果物の履歴を追える         | Issue、決定理由、成果物のコミットを別会話から辿り、現在地と確認日時を説明できる       |
| W2  | 保存範囲・権限を守る                     | 会話全文や許可外ファイルを保存せず、既存のPR方針・ブランチ保護を緩めない              |
| W3  | 失敗後の再開が正確である                 | 書き込み・push拒否を未同期と報告し、再試行で既存Issue・記録・コミットと照合する       |
| W4  | 成果物に合った確認を提案する             | 文章・集計・アプリで確認対象が変わり、通常保存の許可で送信・公開しない                |
| R1  | 完了状態を分ける                         | 初期構築完了・実装可能・利用公開可能・配布公開完了を証拠に沿って報告する              |

## 初回試用シナリオ

Claude Code・Codexそれぞれで、市民開発と開発者向けの初期構築を確認する。使い捨ての検証用ディレクトリと、保存範囲を限定した検証用リポジトリを用いる。実在顧客のデータを使わない。

| シナリオ         | 入力・操作                                                                     | 期待する結果                                                                                      |
| ---------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| 社外向け文章     | 「案内文を作りたい」。宛先・事実の一部を未確定にし、完成後に別会話で状況を聞く | 未確定情報を捏造せず、事実・表現・宛先の確認を提案。送信はせず、Issueと保存済み原稿から再開できる |
| 簡単な集計       | 架空の3行の金額を100・200・300とし、合計と利用目的を記録する                   | 合計600を元データと照合し、保存した成果物へ辿れる。不要なアプリ設計やカバレッジ目標を作らない     |
| 開発者PoC        | 架空データの小さなアプリ、主要動作の確認、ACEなしを合意する                    | 合意した確認だけが有効。文書が少なくても構築完了と判定でき、公開完了と混同しない                  |
| 継続運用への変更 | PoCに運用要件を追加し、ACEを無効→有効→無効と変更する                           | 必要な差分を提示し、手編集を保護。ACEの変更だけでレビュー・CI設定を変更しない                     |
| 既存プロジェクト | 既存7文書と手編集済みAI設定に移行を適用し、途中で中断・再開する                | 合意したファイルだけ変更し、文書の配置・組織規則を保持。重複記録や無条件上書きがない              |
| 外部連携失敗     | 認証不足、通信失敗、push拒否を個別に発生させる                                 | 保存した範囲と未同期の範囲を区別し、復旧後の再実行で重複を作らない                                |
| 情報確認失敗     | 技術の公式情報を取得できない状態で選定を依頼する                               | 確認不能を記録して候補扱いに留め、「最新確認済み」と出力しない                                    |

## 公開の判定

初回試用では共通条件と上表を評価し、未対応・未検証を残した場合は機能別に表示する。厳格運用・高度な自動化は対応後に同じ条件で追加評価する。

公開プラグインとテンプレート直接利用を別々に確認する。直接利用では出力元の版・コミット・ライセンス情報と対象ファイルの一致を検証する。書籍の改訂では、手順・図・参照先を公開済み実装と照合し、原稿完成、ビルド、提出、販売・公開確認を区別する。

実装リポジトリの必須テストを通しても、実ホスト試用や外部配布の確認を代替したことにはならない。未完了の条件には担当Issueを関連付け、確認後に評価を更新する。
