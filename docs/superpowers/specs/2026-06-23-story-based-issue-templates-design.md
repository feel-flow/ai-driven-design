# 設計: Issue テンプレートのストーリーベース化（2軸）

- **日付**: 2026-06-23
- **関連 Issue**: [#446](https://github.com/feel-flow/ai-spec-driven-development/issues/446)
- **ステータス**: 実装完了（PR #447）

## 1. 目的

Issue 起票時に「誰のために・なぜ・完了の判定基準」を着手前に言語化させ、AI が
"もっともらしい仮定" で穴埋めする手戻りを防ぐ。受け入れ条件（AC）を作成時点で
検証可能な形に揃える。

本リポジトリの思想「AI が苦手なのは"コーディング"ではなく"心を読むこと"」と、
ストーリー形式（意図の強制言語化）は同じ方向を向いている。ストーリー化は
このプロジェクトの思想の実装でもある。

## 2. スコープ

### 対象

- `.github/ISSUE_TEMPLATE/`（ドッグフード：本リポジトリ自身の Issue 用）
- `docs-template/.github/ISSUE_TEMPLATE/`（配布：利用者がコピーする雛形）
- `docs-template/06-reference/ISSUE_TEMPLATE_PATTERNS.md`（新規：従来型の集約先）
- `.claude/commands/create-issue.md` / `.claude/commands/refine-issue.md`（スキル連動）
- 関連ドキュメント（`docs/AI_GIT_WORKFLOW.md`, `docs/DESIGN_PRINCIPLES.md`, MASTER 参照網）

### 対象外（Out of Scope）

- pull_request_template.md の刷新
- ラベル体系・release-drafter.yml の変更（カテゴリ分けは既存ラベル駆動のまま）
- Orchestrator / `/loop` 連携、batch refine

## 3. 決定事項（ブレストで確定）

| 論点           | 決定                                                                                    |
| -------------- | --------------------------------------------------------------------------------------- |
| 適用範囲       | **2軸**：feature/docs = ユーザーストーリー、bug/refactor/infra/chore = ジョブストーリー |
| デフォルト     | **ストーリー型 = 推奨デフォルト**、従来型は別パターンとして保持                         |
| 従来型の残し方 | **ライブ（chooser）= ストーリー版のみ**、従来型は解説ドキュメントに集約                 |
| AC 形式        | **ハイブリッド**：Given-When-Then シナリオ + Definition of Done チェック                |
| タイトル       | conventional-commit プレフィックスを残し、記述部をストーリー化                          |
| 対象セット     | `.github/` と `docs-template/.github/` の両方（構造同一、URL のみ差分）                 |

### 2 軸の定義

- **ユーザーストーリー**（feature / docs）

  > **&lt;ペルソナ&gt;** として、**&lt;実現したいこと&gt;** をしたい。
  > なぜなら **&lt;得られる価値／理由&gt;** だから。

- **ジョブストーリー**（bug / refactor / infra / chore）

  > **&lt;どんな状況・トリガー&gt;** のとき、**&lt;どうしたい&gt;** したい。
  > その結果 **&lt;得たい結果&gt;** が得られる。

人格を立てにくい技術系では、状況（トリガー）で語るジョブストーリーが嘘になりにくい。

## 4. タイトル規約

プレフィックスは機械処理（ブランチ名・コミット・PR・リリースノート）用に安く残し、
記述部をストーリー化する。完全な「なぜなら／その結果」は本文先頭のストーリーブロックへ。

| 種別     | タイトル例                                                    |
| -------- | ------------------------------------------------------------- |
| feature  | `feat: 営業担当が月次売上をダッシュボードで確認できる`        |
| bug      | `fix: 1万行超の CSV エクスポートがタイムアウトして完了しない` |
| refactor | `refactor: 認証ロジックをテスト可能な単位に分離する`          |
| infra    | `infra: プレビュー環境を PR ごとに自動発行できるようにする`   |

連鎖の根拠：`Issue タイトル → ブランチ名(feature/#N-...) → コミット(feat: #N ...) →
PR タイトル → リリースノート($TITLE)`。release-drafter のカテゴリ分けは
ラベル駆動のためプレフィックスに依存しないが、グローバル workflow の
conventional-commit 規約との整合のためプレフィックスは温存する。

## 5. テンプレ構造

### 5.1 feature.md（ユーザーストーリー型）

セクション順（既存資産はそのまま下層に温存し、ストーリーを最上位に置く）:

1. `## ユーザーストーリー`（新規・最上位）
2. `## 背景・コンテキスト`
3. `## 参照ドキュメント（AIへ：必ず読んでください）`（現行維持：必須/推奨/スコープ外）
4. `## 6観点（仮定を排除する）`（現行維持：What/How/Where/Constraint/Format/Test）
5. `## 受け入れ条件（AC）`（**新形式**：下記 5.5）
6. `## スコープ外`（現行維持）
7. `## 撤退コスト試算`（現行維持）

ストーリー（why/what）と 6観点（how）はレイヤーが異なり競合しない。

### 5.2 docs.md（ユーザーストーリー型・軽量）

- `## ユーザーストーリー` を最上位に追加（例: 「新規コントリビューターとして…」）。
- 既存の「更新種別チェック」「対象ファイル」「変更内容」は維持。
- AC は新形式（5.5）に置換。

### 5.3 bug.md / refactor.md / infra.md（ジョブストーリー型）

- 先頭に `## ジョブストーリー` を「概要」位置で追加。
- 種別特有セクションは温存する:
  - bug: 再現手順 / 期待される動作 / 実際の動作 / 環境 / エラーログ
  - refactor: Before / After / リスク
  - infra: 変更内容 / 対象環境 / ロールバック手順 / 撤退コスト試算 / リスク
- AC は新形式（5.5）に置換。bug の GWT は「回帰シナリオ」として機能。

### 5.4 general_task.md（ドッグフード専用・ジョブストーリー軽量版）

- 既存の「スコープ確認」を維持しつつ、`## ジョブストーリー`（軽量）を追加。
- 配布側には存在しないため、ドッグフード側のみ更新。

### 5.5 受け入れ条件（AC）の新形式（全テンプレ共通）

```markdown
## 受け入れ条件（AC）

### 振る舞い（Given-When-Then）

- [ ] **Given** <前提状態> **When** <操作> **Then** <期待結果>
- [ ] **Given** ... **When** ... **Then** ...

### Definition of Done

- [ ] テスト追加・既存パス
- [ ] lint / markdownlint エラーなし
- [ ] 関連ドキュメント更新（該当時）
```

bug.md の GWT 見出しは「回帰シナリオ（Given-When-Then）」とし、DoD に
「このバグを再現する回帰テストを追加」を含める。

## 6. 従来型の集約先: `docs-template/06-reference/ISSUE_TEMPLATE_PATTERNS.md`

命名は既存規約（`DECISION_MATRIX.md`, `GLOSSARY.md` の UPPER_SNAKE）に合わせる。

構成:

1. ストーリー型を推奨する理由（"AI は心を読めない" 思想との接続）
2. 2 軸の使い分け表（ユーザーストーリー / ジョブストーリー）
3. **従来型テンプレ全文をコードブロックで保存**（コピペ可能な代替パターン）
4. ストーリー型 vs 従来型の選択ガイド

`06-reference` の索引（README 相当）と `MASTER.md` の参照網にも追加する。

## 7. 2 セットの同期方針

|                 | `.github/`（ドッグフード）            | `docs-template/.github/`（配布） |
| --------------- | ------------------------------------- | -------------------------------- |
| リンク URL      | 具体 repo の `blob/HEAD/...` 絶対 URL | プレースホルダ                   |
| 内容構造        | ストーリー型に統一                    | 同一構造                         |
| general_task.md | ジョブストーリー軽量版に更新          | 対象外（存在しない）             |

既存 ACE 知見の死守:

- テンプレ内ドキュメントリンクは `blob/HEAD/` 絶対 URL（ACE-046）
- アンカーはラベルと URL の両方に `#fragment`（ACE-016）

## 8. スキル連動

### 8.1 create-issue（`.claude/commands/create-issue.md`）

- 手順 3（ヒアリング）: 種別に応じたストーリー要素を収集
  - ユーザー向け: ペルソナ / 能力 / 価値
  - 技術系: 状況 / 動機 / 結果
- 手順 4（検証）: 既存 4 観点に加え「ストーリーが埋まっているか」「AC が GWT+DoD 形式か」を追加
- 手順 5（生成）: body 構造をストーリー型（5.1〜5.5）に更新

### 8.2 refine-issue（`.claude/commands/refine-issue.md`）

- 4 観点バリデーションに第 5 観点「ストーリー有無」を追加
- AC が GWT 構造かをチェック
- 自動補完が書き出す body スケルトンをストーリー型に更新

- `cd mcp && npm run check`（doc 索引チェック）パス

## 11. リスク / 留意点

- テンプレが長くなりすぎると起票の心理的障壁が上がる。ストーリー＋6観点＋撤退コストの
  併載は feature.md で冗長化しやすいため、各セクションの説明文（`>` 注記）は簡潔に保つ。
- 2 セットの構造同期がずれると配布物の品質が落ちる。差分は URL 形式のみに限定する。
- GWT を機械的完了条件まで適用すると冗長。GWT は振る舞い、DoD は機械的項目、と役割を
  明確に分ける。
