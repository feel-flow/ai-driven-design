# AI仕様駆動開発2.0 標準仕様

**対話で目的・制約・進め方を合意し、必要な文書・AI設定・作業管理・検証を一貫して構築する。** これをAI仕様駆動開発2.0（ASDD 2.0）の目的とする。

本書は方法論の正本であり、機能の配布完了を表すものではない。実装、配布用テンプレート、書籍の移行状況は [全体Epic #523](https://github.com/feel-flow/ai-spec-driven-development/issues/523) で追跡する。利用前に [移行ガイド](ASDD_2_0_MIGRATION.md) の対応版確認を行う。文書frontmatterの `version`、方法論の「2.0」、プラグインのSemVer、書籍の版は別々に管理する。

## 1. 用語と適用境界

| 用語         | 定義                                                                                 |
| ------------ | ------------------------------------------------------------------------------------ |
| 利用スタイル | 市民開発／開発者向けという会話と操作の違い。能力・品質の優劣を表さない               |
| 段階         | 試作・PoC／継続運用という成果物の利用段階。市民開発でも継続運用できる                |
| プロファイル | 文書・レビュー・検証・作業管理の初期推奨。固定の必須セットではない                   |
| 合意         | ユーザーの明示的な選択、または明示的に委任された範囲での決定                         |
| 7観点        | MASTER・PROJECT・DOMAIN・ARCHITECTURE・PATTERNS・TESTING・DEPLOYMENTが扱う判断の観点 |
| 適合         | 選択した構成の実際の動作が [適合条件](ASDD_2_0_CONFORMANCE.md) を満たすこと          |

本仕様の必須要件は、合意の保護、記録の正確性、設定の整合などの共通契約に限定する。採用言語、設計パターン、カバレッジ数値、PR運用を全利用先に強制しない。既存プロジェクトの合意や組織規則は、明示的な変更合意なしに緩和しない。

## 2. 対話による初期構築

`asdd-init` を入口に、Claude Code・Codexで次の流れを提供する。専用Webアプリや、利用者向けの独立したスキルコピーは作らない。

1. 既存資料、コード、AI設定、GitHub連携を読み、事実と未決事項を整理する。
2. 目的、利用者、完成条件、段階、公開範囲、扱うデータ、予算・環境の制約を少数ずつ確認する。
3. 推奨構成と代替案について、理由、費用・運用負担、注意点を示す。
4. 必要な設定だけを掘り下げ、作成・変更するファイルと有効になる自動処理を合意する。
5. 合意した内容を反映し、生成物と有効機能を検証する。

質問は「どのDBにしますか」だけで終えず、目的に照らした候補比較を添える。調べれば分かることを質問せず、回答・委任済みの事項を繰り返し確認しない。任せられた細部は決定理由を記録して進める。重要な事業要件や権限の不足は、推測や沈黙によって合意扱いにしない。

### 利用スタイルと個別設定

| 初期推奨     | 文書                       | レビュー・検証                   | 作業管理                     |
| ------------ | -------------------------- | -------------------------------- | ---------------------------- |
| 市民開発     | 短い案内と判断記録         | 成果物・使い道に応じた確認提案   | Issueと成果物の履歴          |
| 開発者・PoC  | 目的・仮説・構成・検証条件 | 簡易レビューと主要動作の確認     | 小さな作業単位の記録         |
| 開発者・標準 | 必要な観点をコア文書へ展開 | 変更範囲とリスクに応じた確認     | ブランチ・PRを基本候補とする |
| 厳格運用     | 判断・検証の追跡と運用要件 | 独立レビューと合意した必須ゲート | 必須チェックを伴う運用       |

ACE、自動振り返り、複数AIレビュー、Hook、CIは独立して選択する。**新規2.0構成ではACEと自動振り返りを初期無効**にする。標準を選んだだけで有効にしない。無効な機能をHookが呼び出したり、実行を促したりしない。

市民開発・PoCであっても、実データ、外部公開、障害の影響に応じて確認を厚くする。厳格運用の詳細と高度な自動化は初回試用後に整備し、未対応の機能は選択候補の対応状態を表示する。

## 3. 7観点と判断の状態

最小構成は `docs/MASTER.md` を短い共通入口とする。7ファイルを先に埋める必要はない。各観点について必要な内容、未決事項、現在不要である理由を整理し、情報量や用途に応じて分離する。

| 観点         | 記録する内容                                          | 分離時の標準パス                     |
| ------------ | ----------------------------------------------------- | ------------------------------------ |
| MASTER       | 索引、目的・使い方、設定、合意・未決事項、Issueリンク | `docs/MASTER.md`                     |
| PROJECT      | 目的、対象者、成功条件、対象外                        | `docs/01-context/PROJECT.md`         |
| DOMAIN       | 業務ルール、用語、具体例・例外                        | `docs/02-design/DOMAIN.md`           |
| ARCHITECTURE | 構成比較、技術選定、セキュリティ                      | `docs/02-design/ARCHITECTURE.md`     |
| PATTERNS     | 採用した実装方針と理由                                | `docs/03-implementation/PATTERNS.md` |
| TESTING      | 完成条件、リスク、確認方法                            | `docs/04-quality/TESTING.md`         |
| DEPLOYMENT   | 配備、監視、復旧、バックアップ、更新運用              | `docs/05-operations/DEPLOYMENT.md`   |

既存の配置は無条件に移動せず、設定と索引で対応付ける。事実・決定の本文は一箇所に置き、AIの入口や他文書から参照する。

| 判断の状態     | 必要な根拠                                           | AIの扱い                                   |
| -------------- | ---------------------------------------------------- | ------------------------------------------ |
| 確認済みの事実 | 資料・コード・実行結果などの出典、必要に応じ確認日時 | 観測した範囲で説明する                     |
| 合意済みの決定 | 選択内容、理由、合意または委任の根拠                 | 採用方針として生成・検証へ反映する         |
| 提案中         | 推奨理由、代替案、注意点                             | 必須ゲートや採用済み仕様へ変換しない       |
| 未決           | 未確認事項、影響、次に決める条件                     | 捏造せず残し、着手・公開を妨げるか区別する |

文書全体の承認状態と、個々の判断の状態を混同しない。一定期間返事がないことを承認とみなさない。

### 一律デフォルトの見直し

| 従来の例                  | 2.0で提示する推奨候補                                                              |
| ------------------------- | ---------------------------------------------------------------------------------- |
| カバレッジ80%以上         | 重要な業務と失敗時の影響から対象を選ぶ。数値目標が必要なら根拠と測定方法を合意する |
| Result pattern            | 言語・フレームワーク・既存コードに合わせ、例外、Result型などを比較する             |
| TypeScript strict常時必須 | 新規TypeScriptでは推奨候補。既存構成では互換性と段階導入を検討する                 |
| マジックナンバー一律禁止  | 業務上の意味や変更理由がある値を定数化し、自明な数値まで機械的に禁止しない         |

同じ見直しをテンプレート、サンプル、AI設定、チェックリスト、検証規則にも適用する。ツールキット自身の開発規約を利用先の採用方針として転記しない。

### 技術バージョンの選定と更新

指定がなければ、最新LTS、または公式に本番利用を推奨するサポート中の安定版を候補とする。採用系列では最新修正版を基本とし、公式のサポート方針、確認日・URL、互換性、依存先・実行基盤の対応、既知の問題を調べる。

新メジャー版は、公開から一律の日数が経てば採用するのではなく、用途と移行検証で判断する。見送る場合は、採用版のサポート期限、見送り理由、再評価条件を残す。更新を続ける担当・頻度・緊急対応・ロールバック方法も運用観点で合意する。公式情報を確認できなければ「最新確認済み」とは記載しない。

例えば、[Node.jsの公式方針](https://nodejs.org/en/about/previous-releases) は本番用途にActive LTSまたはMaintenance LTSを案内し、[PostgreSQLの公式方針](https://www.postgresql.org/support/versioning/) は採用メジャー系列の最新マイナー版を推奨している（方針確認日: 2026-09-08）。具体的な採用バージョンは初期構築時に確認し、これらの製品自体を一律採用しない。

## 4. 入口・設定・再実行の契約

| 入口                                                   | 責務                                                                              |
| ------------------------------------------------------ | --------------------------------------------------------------------------------- |
| `asdd-init`                                            | 対話による初期構築。再実行時は現在の設定から差分による再設定を行う                |
| `asdd-init --check`                                    | 設定・生成物・有効機能の整合を検査する。ファイルや外部状態を変更しない            |
| `asdd-work`                                            | 日常の依頼、再開、進捗記録、状況確認。自然言語から利用できる                      |
| 既存の `init-docs`、`setup-ai-config`、`validate-docs` | 互換入口を維持する。2.0設定がある場合は合意内容を共有し、質問や規則を重複させない |

入口名はスキル名であり、単独のシェル実行ファイルがあることを意味しない。ホストごとの呼び出し方と詳細な設定スキーマは、導入する公式実装の版を参照する。

`.asdd/config.json` を選択構成の正本とし、設定形式の版、利用スタイル、段階、対象AIツール、文書構成、機能の有効状態、合意したGitHub記録先・保存範囲を記録する。認証情報を保存しない。初期化処理が出力する管理情報には、管理対象ファイルと生成時点の状態を残す。

再設定では、管理対象の手編集と生成差分を照合し、衝突を提示する。無条件の上書き・削除を行わず、途中中断から再開しても合意・手編集を失わない。未知・不正な設定を既定値として黙って読み替えない。2.0設定のない既存プロジェクトは、明示的に移行するまで従来動作を維持する。

`CLAUDE.md`・`AGENTS.md` は共通文書への薄い入口とし、ツール固有設定だけを分離する。必要なHook・スクリプト・CIだけを配置し、ホストが対応しない機能を有効化済みと報告しない。スキルは公式のプラグイン導入を使い、`SKILL.md` の複製・ミラーで配布しない。

## 5. 市民開発の日常利用

利用者には「Issue」「PR」を必須語彙にせず、「やりたいこと」「できたこと」「確認待ち」「次の一歩」で説明する。GitHubは記録先として使い、一つの目的・成果物を一つのIssueで追う。記録先、保存範囲、通常保存の自動化を初回に合意する。

- 目的、完成条件、現在地、決定・理由、未決事項、成果物、次の作業を記録する。会話全文は保存しない。
- 専用リポジトリは非公開を推奨し、所有者・名称・保存対象を合意してから作成する。
- PRを使わない保存方針を選んだ専用リポジトリでは、許可された成果物をコミット・pushする。既存プロジェクトのPR方針とブランチ保護は引き継ぐ。
- 作業の再開・状況回答では最新のIssueと履歴を読み、確認日時、完了・進行中・確認待ちを説明する。古い記録しか取得できなければ明記する。
- 通信・認証・push失敗は「未同期」と報告する。再開時に既存記録を照合して重複を防ぎ、記録失敗を保存完了にしない。
- 公開、他者への送信、破壊的操作は通常の記録保存と区別し、承認された対象・範囲に従う。Issue完了は、合意した完成条件の達成を根拠にする。

文章なら事実・表現・宛先、集計なら元データとの一致、アプリなら主要動作など、成果物に応じた確認を提案する。社外向け文章のレビュー提案を、自動送信の許可と解釈しない。

## 6. 適合と公開状態

2.0対応版の `validate-docs` は選択した文書構成と段階を評価し、未作成の任意文書をエラーにしない。未決事項を完成済みにもしない。MCPの文書検索は最小構成でも利用できる状態を維持する。従来の `/validate-docs` や本リポジトリの `npm run validate` は7文書を必須とするため、最小構成には対応版を使う。旧検証しか使えない場合は制約として記録する。実際の適合確認は [適合条件と試用シナリオ](ASDD_2_0_CONFORMANCE.md) に従う。

| 到達点         | 必要な証拠                                                       |
| -------------- | ---------------------------------------------------------------- |
| 初期構築が完了 | 合意した生成物・設定・有効機能が整合し、残る未決事項を説明できる |
| 実装可能       | 着手する作業の目的・完成条件・必要な決定が揃っている             |
| 利用・公開可能 | 対象成果物の検証、運用・公開条件、必要な承認が揃っている         |
| 配布・公開完了 | 対象の版・配布先・実際の利用経路で反映を確認できる               |

2.0の公開方法論は本リポジトリ、スキル・生成処理・配布テンプレートは `feelflow-plugins`、公開プラグインは `ff-dev-toolkit` への一方向同期、書籍原稿は `ai-books` を正本とする。同一内容を各リポジトリで独立改訂しない。公開側で編集する標準・案内は [編集元の限定リスト](../scripts/public-owned-docs.json) で保護し、他の同期元で上書きしない。非公開の詳細知見・事例は別管理を維持する。直接利用用テンプレートの同期は [Issue #525](https://github.com/feel-flow/ai-spec-driven-development/issues/525) で追跡する。
